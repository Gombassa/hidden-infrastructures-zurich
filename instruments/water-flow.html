Simulated pipes

distance in metres · condition: main or connection

Real water pipes carry no pipeType property at all — that field is only ever derived for sewage (gravity/pressure, from a different layer-code family); it was never added for water. The only categorical signal water pipes carry is diameterClass, the trailing digit of the DXF layer code (LKZ131X) — confirmed present on all 10,568 pipe LineStrings in lk-water.geojson (never null; the 4,655 nulls in the file are all fitting Points), with 7 distinct values: 0, 3, 4, 5, 7, 8, 9. Checking the raw layer string confirms it carries no information beyond that digit — every water pipe's layer is exactly LKZ131X-MLU1, a strict 1:1 match with diameterClass, so there is nothing independent left to cross-tabulate against.

docs/phase2-data-layer.md names two values by function — 4 = distribution (main), 5 = connection — but not the rest, and the city's own LK legend PDF stops at a coarse <500mm/≥500mm cartographic split, no code table. The previous version of this instrument ranked the remaining five values by inverse feature count, which is unsound: counts are per digitised LineString segment, not per physical pipe, and a long main gets cut into many short segments while a house connection is often one run — rarity by segment count can invert the thing it's meant to infer.

Replaced with segment-length distribution, which separates cleanly: classes 3, 4, 9 have mean segment length 19.6–26.6 m with 26–33% of segments over 20 m; classes 0, 5, 7, 8 have mean 2.75–4.55 m with under 4% over 20 m — close to an order of magnitude apart, and the confirmed pair falls cleanly either side (4 in the long group, 5 in the short group). Mains = {3, 4, 9}, connections = {0, 5, 7, 8}. Only 4 and 5 are documented; 0, 3, 7, 8, 9 are inferred from length, not from any named source — see WATER_PIPE_CONDITION in the script for the per-value comment. This is pipe function, correlated with diameter but not verified against an actual diameter table — WVZ has not published one.
